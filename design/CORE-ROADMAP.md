# EternalOS Core Roadmap

> Authored 2026-11-11. **Authoritative plan — supersedes `RELEASE-READINESS.md`** (now a reference appendix) and the archived `ROADMAP.md`.
>
> **Principle: get the core product right before adding new surfaces.** "Core" here is the product people actually touch every day — the desktop and files, how they customize it, how they create apps, and how they talk to the agent. Platform expansion (social, a mobile rebuild, MCP publishing, a marketplace v2, federation) is explicitly **parked** until these four are solid.

Status legend: ✅ Done · 🟡 Partial · ❌ Not started · 🔎 Needs a reliability pass (works, under-tested or rough).

> **Security + reliability hardening pass (2026-11-12 → 13, branch `cursor/w2-css-sanitizer`).** A sweep of the auth, app-bridge, bazaar, upload, visitor, and customization surfaces. Real bugs found and fixed, each with a regression test where the harness can drive it (the Worker-Loader app/game bridge reads a separate DO namespace under `unstable_dev`, so a few bridge-only fixes are covered by reasoning + adjacent tests):
> - **App fs scope escape (write):** `EternalService.write` authorized the claimed `path` while an out-of-scope `parentId` decided placement → an app could write into any folder whose id it knew. Now authorizes the real target path.
> - **App privilege passthrough (patch):** `EternalService.patch` forwarded `updates` to the owner-facing DO allowlist → an app could set `isPublic` / `parentId` / `grantedPermissions` on items it can write. Now filtered to benign content fields.
> - **SSRF false-positive:** the app-fetch guard treated any DNS host starting with `fc`/`fd` (fcc.gov, fdic.gov) as a private IPv6 address and blocked granted fetches. Gated the IPv6 ULA check on the host being an IPv6 literal.
> - **dev-deploy status codes:** external-import and IPC declaration errors mapped to 500 instead of 400.
> - **Game-save lockout:** the rate limiter re-set its TTL every write, locking out an actively-saving player mid-session; switched to a fixed window.
> - **Variants never persisted:** the profile allowlist dropped `variants`, so window-chrome selections were lost on reload/new device and never reached visitors. Added + validated the field.
> - **Visitor appearance lost from cache:** `handleVisit`'s cache path returned the nested `{items,profile,windows}` snapshot while the client reads flat appearance fields, so a cached visit (populated on every mutation) dropped ALL custom appearance. Both paths now flatten through one builder.
> - **Username normalization:** signup/change-username validated the raw input but stored the normalized one (`"___"` → empty handle, `"_bob"` → `bob`). Now re-validates the normalized value.
> - **OAuth CSRF fail-open:** `verifyOAuthState` returned `null === null` → true with no stored state; now fails closed (it is the sole CSRF guard — the server callback never sees the state).
> - **Link-item stored XSS:** item `url` was stored unvalidated and rendered as an `<a href>` / opened in the website viewer, so a public `javascript:` link item was stored XSS against any visitor who clicked it. Now restricted to http(s) on write (matching profileLinks), with an inert-text render guard in GetInfo as defense in depth.
> - **Secret in GDPR export:** the data export stripped `passwordHash` but left `recoveryCodesHashed` (password-equivalent). Now stripped too.
> - **Agent thread titles:** user-supplied create/rename titles were uncapped (auto titles cap at 60); bounded to 100 to keep the per-user thread-list KV value under its size limit.
> - **Defense in depth:** `nosniff` on all upload serve paths; DOM-apply guards so the appearance store is testable; de-flaked the worker suite against transient non-JSON runtime errors.
>
> New integration coverage: the full auth lifecycle (recovery-code login + regeneration, change-password session invalidation, change-username normalization/uniqueness, cancel-deletion, GDPR export secret-stripping), agent thread CRUD + per-user isolation, fs-scope + patch-field + SSRF boundaries, profile variants round-trip, and the link-URL XSS guard. Frontend: appearance store actions, the visitor transform, and the OAuth state check. Worker suite 20 → 34, frontend 44 → ~310.
>
> Audited and found clean (no bug): bazaar publish/install + estheme, the designTokens/customCSS validators, app storage (KV) sandboxing, profile field filtering, game cross-isolation + sandbox grant, `fsPolicy` glob matching, `getPublicItemsFiltered` (fails closed), the cartridge validator, og:image escaping, the refresh-token rotation + reuse detection, recovery-code entropy, agent chat capability tokens (purpose-bound), analytics dedup, and the sound/cursor serve routes.
>
> **Test harness:** the worker integration suite now runs against a fresh ephemeral `persistTo` temp dir per run (not the shared `.wrangler/state`), so it is hermetic — no state leaks between runs, no dev-account pollution, and the previously flaky/slow `hard-deletes an account…` test (which scanned a KV bloated by accumulated test signups) now runs in ~0.25s and is stable. Note: a large `.wrangler/state` from earlier runs can be cleared; it is no longer written to by tests.
>
> **App-listing exposure fix (2026-11-19, sandbox-review follow-up).** The app bridge's `fs.list` has always skipped `type: 'app'` items (EternalService — "apps don't list themselves to apps"), but the capability-token REST list (`GET /api/apps/:appId/fs/list`) still included them, so an installed app holding a `/**` read grant could enumerate installed app names and ids (reading them already 404s; no manifest/grant data leaked — information exposure only). The REST list now applies the same skip; the owner's own desktop list is unchanged. Audited every app-scoped list surface: the bridge `fs.list` (already skipped), the REST `fs/list` (fixed), REST `fs/read` (item-level, app items 404), `?ft=` file tokens (single-file serving only), and game capability tokens (game saves only). Regression test drives both list paths plus the owner view. While writing it, two harness facts got corrected: the bridge under `unstable_dev` DOES read the same DO state (the earlier "separate DO namespace" note was masking this), and the compiled worker's `clampInt` maps a missing `limit` to 1 (Number(null) is 0, not NaN), so a bare bridge `fs.list` only ever returns the first item — bridge assertions must pass `?limit=500`; that quirk itself is a follow-up, not fixed here.

## How to read this

Four core workstreams, each with: where it stands, what to do (ordered), and what "good" looks like. Underneath them sits **Foundations** — cross-cutting reliability that every workstream depends on. A surface is not "done" until its acceptance bullets have recorded evidence (a test or a logged manual run), not just a passing build.

Verification baseline that already holds (re-run 2026-11-11): both typechecks, frontend build, lint, and all tests pass (21 frontend + 19 worker). The solid substrate — JWT + refresh rotation, bcrypt, per-user `UserDesktop` Durable Object on SQLite, magic-byte upload validation, strict CSP/HSTS/env-aware CORS, public-asset + visitor-WS rate limiting, and Dynamic Workers as the sandboxed app runtime — is real and should not be rewritten.

## Workstream 1 — Core functionality (desktop, windows, files)

The thing EternalOS *is*: a draggable desktop of windows, icons, folders, files, and widgets that survives reload and connection loss.

**Where it stands** — 🔎 Mature but under-tested. `Desktop.tsx` (~2,000 lines) still carries interaction, rendering, and commands together, but the desktop store's state model is now explicit (item 4: acknowledged/optimistic/interaction state separated, see below). The body-drag/click-swallow bug is fixed and must stay fixed. Viewers exist for text, code, markdown, PDF, image, audio, video, and websites; widgets for sticky notes, link boards, music, pixel canvas, and a guestbook.

**Do (ordered):**
1. ✅ **Done — R3 closed:** the position-save path now queues through `persistItemMutation`, rolls back to the last server-known position on failure (even across a rapid drag), and surfaces a "Sync Failed" error. A broader saved/saving/failed *status indicator* for editors/settings is still a nice-to-have, tracked under Workstream 4's save-status work.
2. ✅ **Done — accessibility bugs fixed (both halves test-covered, 2026-11-19):** ContextMenu keyboard nav + menu roles and the AlertDialog focus trap / title linkage / scoped Enter were implemented 2026-11-11 (see the Foundations note). **ContextMenu half:** roles + roving keyboard nav landed with the 2026-11-11 pass; the remaining gaps are now closed — Escape restores focus to the element that had focus before the menu opened, and Tab closes the menu — and the full contract is pinned by `ContextMenu.test.ts` (real component render under the repo's node-env test DOM): `menu`/`menuitem`/`menuitemcheckbox`/`separator` roles with `aria-disabled`/`aria-checked`, initial focus on the first enabled item, ArrowUp/ArrowDown wrap skipping disabled items, Home/End, Enter/Space activation, Escape close + focus restore, Tab close, plus mouse-click activation guards. The menu API has no submenus, so `aria-haspopup`/`aria-expanded` has nothing to apply to. **AlertDialog half:** the same node-env test DOM pins it too (`AlertDialog.test.ts`): `role="alertdialog"` + `aria-modal` + `aria-labelledby`/`aria-describedby` linked to title and message via `useId` (message doubles as the name when there is no title), initial focus on the primary action — the established pattern here, every call site marks its default action primary, à la classic Mac alerts — with a first-action fallback for button sets without a primary, Tab/Shift+Tab wrapping that also pulls escaped focus back inside, Enter activating only the focused button (Enter on Cancel cancels; Enter outside the dialog does nothing — no global Enter listener), Escape cancelling, and focus restored to the opener on close. Remaining follow-up (separate task): Desktop.tsx's document-level icon-navigation shortcuts (Tab/Enter/Escape on selected icons) still fire while any modal is open and need their own gating.
3. ✅ **Harden the reliability matrix with tests** (substantially done): create/delete/update/position, **trash/restore/empty-trash**, and **cut/paste** (`pasteItems`) have optimistic-write rollback + failure surfacing with tests (`desktopStore.test.ts`) — a failed move/trash/restore no longer leaves an item looking moved/(un)trashed when the server never recorded it, and a refused empty-trash restores the trashed items from the acknowledged snapshot (2026-11-19) instead of leaving them gone locally. **Window restoration** across reload / connection-loss is now covered (`windowStore.test.ts`): restores from localStorage, falls back to server windows on a new device / cleared cache, drops windows whose item was deleted, discards corrupt state, and clamps off-screen windows into the viewport. **Deterministic search** is now done: the ranking was extracted from `SearchWindow` into a pure `utils/search.ts` (`searchItems`) and given a total-order tiebreak (score → recency → **id**), so equal scores/timestamps no longer produce non-deterministic ordering; covered by `search.test.ts` (determinism, AND semantics, synonym vs exact ranking, trashed exclusion, limit). **Upload reliability** is covered (`desktopStore.test.ts`): a successful upload adds the item and completes its progress entry; a failed upload leaves no phantom item and marks the entry errored; a late upload after an account switch can't populate the next account. (Worker-side upload validation + quota accounting already have integration coverage.) **Folder creation** goes through `addItem` (a folder is just `type: 'folder'`), so it's covered by the failed-create rollback test. **Resize persistence** is covered (`windowStore.test.ts`): a resize enforces the 200×150 minimum and round-trips through localStorage to survive reload. Rename rides on `updateItem` (partially covered). **Settings half of the "Good when" (2026-11-19):** every user-visible save path outside `desktopStore` was audited against forced offline / 401 / 429 / 500 and the failures fixed, each with a regression test (`authStore.test.ts`, `appearanceStore.test.ts`, `soundStore.test.ts`, `ProfileWindow.test.ts`, `QuickStartWizard.test.ts`): the appearance save no longer mirrors a refused rice into localStorage as if saved (it stays painted-but-unsaved and the caller surfaces the error — the AppearancePanel/CSSEditor pattern); the six optimistic profile setters (wallpaper, wallpaper mode, bio, profile links, share description, analytics — the privacy toggle) now serialize per field, roll back to the last server-acknowledged value on refusal, and report failure so their surfaces can say so (`ProfileWindow` keeps the edits in the editor with an error instead of a false "Saved!", `ShareDialog` shows Saved only on ack, the analytics toggle reverts with a visible error, wallpaper select/upload reports failure); the sound-pack mapping sync moved into the store (`saveCustomSoundPack`) with rollback — this exposed a latent bug where `setCustomSoundUrl` mutated the pack in place, corrupting any previously captured rollback target; the QuickStartWizard no longer commits the preset before the server accepts it (it reverts to the last acknowledged rice on refusal, and its wallpaper is only adopted after the PATCH acks). CSS-history restore was audited clean (applies the reverted profile only on success, shows the error otherwise); the watermark and display-name paths in `PreferencesWindow` were already correct; `themeStore` is vestigial (no consumers, no server sync — theme-selection saves go through the appearance store and the wizard). **The W1 reliability matrix is now substantially complete.**
4. ✅ **Separate acknowledged server state from interaction state** in the store (prerequisite for the above being testable); extract desktop commands/persistence from `Desktop.tsx` only as far as the tests need. **State-model split done (2026-11-19):** the store's model is now explicit. The data slice holds the *displayed* (optimistic) items; `desktopItemSync.ts` owns the *server-acknowledged snapshot* (last server-confirmed value per item) plus all pending-mutation bookkeeping — the per-item write queue `persistItemMutation` moved there unchanged in semantics, and rollbacks now target the acknowledged snapshot per attempted field with the existing not-re-touched guards, instead of ad-hoc closure snapshots. The selection moved to `desktopSelectionSlice.ts`, a separate slice sync/reconcile code never writes (`setItems`/`loadDesktop` refresh items + snapshot only; `removeItem`/`moveToTrash` shrink it through `dropFromSelection`; session reset through `deselectAll`) — so interaction state provably survives a server reconcile. Making the rollback target the acknowledged snapshot fixed three real "successful-looking unsaved item" gaps, each pinned by a regression test verified to fail on the old code: two chained renames that both fail used to leave the *intermediate optimistic* name displayed; a rename whose save fails while the user drags the same item used to skip rollback entirely (now the name reverts, the newer move is kept); and a position save failing after an earlier save landed used to leave the newer unsaved position (the old code deleted its rollback target on the first success). Reconcile coverage added (`desktopStore.test.ts`, 44 → 57): server echo after an optimistic create converges to one item (no duplicate), failed writes roll back to the acknowledged snapshot, successful writes/loads refresh it, and interaction state survives both `loadDesktop` and `setItems` reconciles. **The `Desktop.tsx` extraction (deliberately minimal — only as far as the tests need):** its commands/persistence all flow through the store's public actions and the new tests are store-level, so nothing needed lifting except one command (below). **The bypass paths this note left open are closed (2026-11-19, desktopgaps):** the fire-and-forget sort/clean-up saves now route through the per-item write queue (`arrangeAndPersist` in `desktopStore.ts`) — a refused batch reverts each failed item to its acknowledged position and surfaces one shared "Sync Failed", and a sort waits for an earlier in-flight save on the same item instead of overtaking it; `emptyTrash` restores the trashed items from the acknowledged snapshot when the server refuses the permanent delete; and the one raw `apiUploadFile` call in `Desktop.tsx` — the "Add Sticker..." flow, mislabeled "wallpaper" above (the actual wallpaper paths go through `setWallpaper`/WallpaperPicker and were already covered) — is extracted to `components/desktop/stickerUpload.ts` and now drives the store's `uploadFile` + `updateItem`, so a refused upload leaves no item ("Upload Failed") and a refused apply rolls the item back to the acknowledged plain image ("Sync Failed"); the old flow's apply silently no-oped because the raw upload never added the item to the store, so stickers never actually appeared. Each fix is pinned by regression tests verified to fail on the old code (`desktopStore.test.ts`, 57 → 69 tests, plus `stickerUpload.test.ts`). Known worker-side follow-up (not fixed here, out of the task's file scope): the item-update allowlist strips `type`, so an applied sticker reverts to a plain image on the next server reconcile.

**Good when:** forced offline, 401, 429, and 500 never leave a successful-looking unsaved item or privacy setting — ✅ both halves covered with tests (items: `desktopStore.test.ts` for desktop items; the 2026-11-19 settings-half note above for every save path outside it); reconnect converges to one consistent result with no duplicates; core actions are keyboard-reachable; the drag never swallows a click on a list row or tab.

Half the product's personality. Today it spans custom CSS, color tokens, typography, variants, wallpaper, cursors, sounds, sprites, icons, and CSS assets.

**Where it stands** — 🟡 Rich but fragmented. The token pipeline (`CustomAppearance` → `resolveTokensFromAppearance` → `compileTokensToCSS` → DOM) works; CSS is sanitized and scoped to `.user-desktop`; CSS history/restore exists; presets live in `onboardingPresets.ts`. The `.estheme` single-file skin format (export/import/fork/nest) is **designed and partially built** — manifest validator, mirrored frontend schema, builder, parser, and an export helper exist — but bazaar still publishes a flat token blob, not CSS + cursors + sounds + wallpaper as one unit.

**Do (ordered):**
1. ✅ **Preset readability matrix (automated floor done):** every shipped preset is now guarded by `onboardingPresets.test.ts` — structural shape, valid-hex ink colors, a 3.0:1 contrast floor on the authored text/background pairs (title/button/label), a clean token-pipeline compile, and customCSS that sanitizes scoped + remote-free. This caught + fixed a real one (Y2K: white title text on hot pink, 2.65:1 → dark-magenta `#8B0040`, 3.65:1). **Follow-up (optional):** an in-browser manual pass for the gradient/glass surfaces (XP, Frutiger Aero) whose text contrast can't be computed from hex.
2. **Lock down the customization round-trip:** save/reload, reset, CSS sanitization, CSS history restore, and theme import/export each need a test. Sanitizer regressions are a security surface, not just cosmetics. ✅ **Done:** the CSS sanitizer was extracted from `appearanceStore` into a pure, unit-tested `utils/cssSanitizer.ts` (url() allowlisting, `@font-face` stripping, `.user-desktop` scoping — covered by `cssSanitizer.test.ts`), and the save/reload round-trip (`profileToAppearance` ↔ `appearanceToProfileFields`, `buildTokenUpdate`/`getTokenValue` token routing) is covered by `appearanceStore.test.ts`. The token compiler itself (`resolveTokensFromAppearance` → `compileTokensToCSS`, the pipeline core) is now directly covered by `tokenCompiler.test.ts` — var mapping, derived text colors (and their hex-only guard), font smoothing, window opacity clamps, title-bar rules, and the custom-cursor-URL security allowlist. **CSS history restore is now covered end to end** (2026-11-19): the worker suite pins the `/api/css-history` revert contract (full-profile preservation, history recording, unknown-version rejection) and the frontend restore path (`applyCSSRevertProfile`) re-applies the whole profile through `profileToAppearance`. **This surfaced + fixed a real bug:** the CSSEditor restore hand-rolled its field list and silently dropped typography, `windowOpacity`, `designTokens`, and `variants` — restoring an old CSS version wiped them from the session and localStorage until the next full sync. `resetAppearance` is now covered too: extended state (tokens/variants/fonts/opacity) is dropped, an unsaved reset leaves the last saved appearance in localStorage, and reset+save persists `{}` locally. ✅ **Done — the reset/server-clear gap (2026-11-19):** the profile PATCH now has an explicit clear semantic — an appearance field sent as `null` means "remove this saved field". `UserDesktop.updateProfile` gates `null` to exactly the fields the frontend reset is meant to clear (the legacy appearance fields + `designTokens` + `variants`): it deletes them from the stored profile, so GET /profile shows them gone and a reload after Reset + Save shows the reset state. `null` for any other allowlisted field (username, wallpaper, bio, soundPack, …) is a 400, and fields outside the allowlist (uid, email, auth material) keep today's unknown-field behavior of being silently ignored; non-null values validate exactly as before. The frontend side: reset (and preset switches / per-control clear buttons) mark fields as `undefined` in the appearance store, and `appearanceToProfileFields` sends those as `null` tombstones. Covered by the worker suite (null-clear round-trip + protected-field rejection + unchanged validation) and `appearanceStore.test.ts` (the reset payload carries `null` for every reset field). Nuance: clearing `customCSS` via `null` records no `''` CSS-history entry — the history still lets you restore any pre-reset version.

## Workstream 3 — App creation

The platform bet: generate real, editable, sandboxed apps from natural language. Architecture is settled (see [12-orchestrator-v2.md](12-orchestrator-v2.md), [13-source-first-app-workspaces.md](13-source-first-app-workspaces.md), [01-apps-interop.md](01-apps-interop.md)); execution stops one layer short.

**Where it stands** — 🟡 Strong substrate, thin pipeline. `buildAppFromPrompt` already does server-side structured generation; apps run as Dynamic Workers with a constrained `window.eternal` bridge (`fs.list/read/readText/readJson/urlFor`, `profile.get`); both `source.json` and `bundle.json` are persisted. **urlFor capability fix (2026-11-19):** an installed app's bridge requires `Authorization: Bearer <capability>`, which a bare `<img src>` fetch cannot send, so the old plain-URL `fs.urlFor` 401'd even for in-scope items — the bridge runtime now performs the authorized fetch itself and resolves a cached blob: object URL (revoked on `pagehide`); capability-free previews keep the plain loopback URL, and the API is documented as async so generated apps `await` it. Server auth is unchanged — no query-string token was added. But `createWorkerModuleFiles()` still privileges one HTML/one CSS/one JS entrypoint, and declared vs. granted permissions aren't separated. Generation now runs brief → spec → files (the explicit spec stage landed 2026-11-19, see Phase A below) instead of brief → files.

**Do (ordered — maps to the orchestrator rollout):**
1. **Phase A — builder shape:** add an explicit `buildSpecFromPrompt()` stage ahead of file generation; make validation rules first-class (permissions, asset references, empty states) instead of relying on bundle errors; improve repair prompts with the actual compiler/runtime errors. Demote curated templates to test fixtures only. 🟡 **Partial — explicit spec stage + derived permissions done (2026-11-19):** `buildSpecFromPrompt()` now runs ahead of file generation on the build and preview paths and produces a typed `AppSpec` (`src/agents/tools/appSpec.ts`: name, a one-line purpose that becomes the manifest description, screens with per-screen empty states, fs data reads, `eternal.storage` keys, network domains, profile fields, ipc topics). The spec is validated deterministically BEFORE any file is generated — unknown permission kinds, network domains that aren't hostnames, empty screens, unscoped or malformed fs globs/mime types, invalid storage keys, and data-reading screens without empty states each produce a structured `spec/*` issue fed back into the spec repair loop by code. Manifest permissions are now DERIVED from the spec (`derivePermissionsFromSpec`) rather than declared separately by the file generator: the files prompt is handed the exact derived permissions and told to stay inside them, which makes "permission used but not declared" structurally rare. `dataReads` derive fs read/mimeTypes; `dataWrites` derive `fs.write`/`fs.delete` path globs (the same manifest shape chat-supplied apps declare — write mime types are generator guidance only), with whole-desktop write scopes rejected unless the spec explicitly marks the app a file manager (`arbitraryFiles`, validated as `spec/broad-fs-write`); `storageKeys` remain permission-free for the app's own private state, so the spec model picks where each kind of state lives. Covered by unit tests for validation + derivation and by scripted fake-AI-binding tests proving the spec stage runs first, its derived permissions land in the manifest (desktop item + `metadata.json`), and an invalid spec is repaired by issue code before any file exists. The files-stage repair prompts already embed the exact `appBundleValidation` issue codes (`formatAppValidationIssues`). Remaining for Phase A: curated templates are still a chat-visible tool (`createCuratedApp`) — demotion to test fixtures pending. Earlier progress, still holding: `validateGeneratedApp` (the source gate the dev-deploy and AI-build paths share) now has adversarial coverage via `/api/apps/dev-deploy` in `worker.integration.test.mjs` — external script/stylesheet links, external dynamic + static imports, fs-read/profile/network/ipc usage without the matching declared permission, missing local asset refs, missing HTML entrypoint, and a positive declared-permission control. **This surfaced + fixed a real bug:** the dev-deploy catch block mapped thrown validation messages to HTTP status by prefix, but the prefixes for external imports (`Dynamic imports…`, `Imports from…`) and IPC declaration errors (`App emits/listens…`) were missing, so those client-supplied bad bundles returned **500** (server fault, trips 5xx alarms) instead of **400** — fixed in `routes/apps.ts`.
2. ✅ **Phase B — permission mediation (2026-11-19):** declared vs. granted permissions were already separated (manifest declares, the permissions route grants within the declared set, dev-deploy updates never widen grants — pinned by the escalation-guard integration test). The missing half is now in: per installed app, each granted scope carries approval metadata (`grantedPermissionApprovals` on the app's DesktopItem — approvedAt, approved-by uid, and the manifest's rationale as it read at approval time), exposed by the app-permissions GET so the UI can show "approved on …". **Broad scopes need explicit approval:** fs read/write/delete on an all-files glob (`**`, `/**`, `**/*`, `/`), any wildcard network domain (`*`, `*.example.com`), and all four profile fields count as broad (`worker utils/appScopes.ts`, single source of truth). The server rejects a grant request containing a broad scope without that scope's explicit tick (400 with the unticked scope list); the install/approval dialog (extracted to `components/apps/AppPermissionDialog.tsx`) renders broad scopes as distinct `--danger` warning rows carrying the rationale, never pre-ticks them, and sends each tick as a `broadApprovals` entry — narrow scopes keep today's flow. Legacy installs are migrated lazily: grants without stored metadata read as approved with approvedAt unknown, and re-requesting a broad grant still requires the tick. Denying the dialog no longer rewrites the (unchanged) grant set server-side, so a denial can't re-date existing approvals. Coverage: unit tests for the scope/approval helpers (`appScopes.test.mjs`), integration tests for the 400 rule + junk-flag handling, approval metadata persistence (incl. the approval-time rationale surviving a manifest change and pruning on revoke), and the lazy-migration read path; the frontend dialog's broad-scope gating is pinned by a real-render vitest suite. ## Workstream 4 — Agent (Ask Eternal)

The conversational front door to everything above. `OrchestratorAgent` (DO) over WebSocket, 3-pane chat UI, tools for apps, desktop, and memory.

**Where it stands** — 🔎 Works, needs a reliability + controls pass. Transport is `useAgent`/`useAgentChat` over WebSocket; threads via REST. Intent routing is a pure, table-driven classifier in `agents/intent.ts` (see item 4). Chat colors derive from theme vars via `color-mix()`. Locally (AI binding off) the UI works but replies error.

**Do (ordered):**
1. **Transport reliability:** first message, streaming, stop, reconnect, and thread-history reload must all produce coherent outcomes; a dropped socket mid-stream recovers without duplicate or orphaned messages.
2. **Tool-call correctness:** exercise `appTools`, `desktopTools`, `memoryTools` end to end, including the mutation **approval** flow — rejection and acceptance both reconcile correctly, and a rejected approval never half-applies.
3. **Per-account controls:** usage and concurrency limits so one account can't exhaust AI budget or pin the DO; graceful, legible handling of provider failure.
4. ✅ **Done — intent routing extracted and table-driven (merged earlier; roadmap line updated 2026-11-19):** the brittle inline regex router moved out of `OrchestratorAgent.ts` into `packages/worker/src/agents/intent.ts` — a pure, single-message classifier (`classifyRoute`) whose patterns are built entirely from auditable vocabulary tables (hard/soft app verbs, strong/weak app nouns, genre words, negators), so tuning is a table edit, not a regex rewrite. Editing an app vs. building one vs. plain chat is unambiguous by construction: both edit and build phrasings route to `app-build` (one app-builder toolset serves creating and mutating), so neither falls through to chat; everything unrecognized falls to `chat` on purpose. The route table (`app-install-preview`, `app-build`, `app-read`, `desktop-write`, `desktop-read`, `chat`) and the documented boundaries (single-message scope, clause-scoped negation, imperative-only verb morphology, deliberate non-English fallthrough) live in the module header, and the contract is pinned by the table-driven `packages/worker/test/intent.test.mjs` — 145 realistic phrasings across build/edit/read/install-preview/desktop/chat requests, negated commands, casual "app" chat, and app questions that are not commands — which runs in the plain `node --test` worker suite.

**Good when:** streaming/stop/reconnect/history never corrupt a thread; every tool and the approval flow have coverage; provider or budget failure degrades to a clear message, not a stuck spinner.
