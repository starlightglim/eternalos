# EternalOS Core Roadmap

> Authored 2026-11-11. **Authoritative plan — supersedes `RELEASE-READINESS.md`** (now a reference appendix) and the archived `ROADMAP.md`.
>
> **Principle: get the core product right before adding new surfaces.** "Core" here is the product people actually touch every day — the desktop and files, how they customize it, how they create apps, and how they talk to the agent. Platform expansion (social, a mobile rebuild, MCP publishing, a marketplace v2, federation) is explicitly **parked** until these four are solid.

Status legend: ✅ Done · 🟡 Partial · ❌ Not started · 🔎 Needs a reliability pass (works, under-tested or rough).

> **Security + reliability hardening pass (2026-11-12 → 13, branch `cursor/w2-css-sanitizer`).** A sweep of the auth, app-bridge, bazaar, upload, visitor, and customization surfaces. Real bugs found and fixed, each with a regression test where the harness can drive it (the Worker-Loader app/game bridge reads a separate DO namespace under `unstable_dev`, so a few bridge-only fixes are covered by reasoning + adjacent tests):
> - **App fs scope escape (write):** `EternalService.write` authorized the claimed `path` while an out-of-scope `parentId` decided placement → an app could write into any folder whose id it knew. Now authorizes the real target path.
> - **App privilege passthrough (patch):** `EternalService.patch` forwarded `updates` to the owner-facing DO allowlist → an app could set `isPublic` / `parentId` / `grantedPermissions` on items it can write. Now filtered to benign content fields.
> - **SSRF false-positive:** the app-fetch guard treated any DNS host starting with `fc`/`fd` (fcc.gov, fdic.gov) as a private IPv6 address and blocked granted fetches. Gated the IPv6 ULA check on the host being an IPv6 literal.
> - **dev-deploy status codes:** external-import and IPC declaration errors mapped to 500 instead of 400.
> - **Game-save lockout:** the rate limiter re-set its TTL every write, locking out an actively-saving player mid-session; switched to a fixed window.
> - **Variants never persisted:** the profile allowlist dropped `variants`, so window-chrome selections were lost on reload/new device and never reached visitors. Added + validated the field.
> - **Visitor appearance lost from cache:** `handleVisit`'s cache path returned the nested `{items,profile,windows}` snapshot while the client reads flat appearance fields, so a cached visit (populated on every mutation) dropped ALL custom appearance. Both paths now flatten through one builder.
> - **Username normalization:** signup/change-username validated the raw input but stored the normalized one (`"___"` → empty handle, `"_bob"` → `bob`). Now re-validates the normalized value.
> - **OAuth CSRF fail-open:** `verifyOAuthState` returned `null === null` → true with no stored state; now fails closed (it is the sole CSRF guard — the server callback never sees the state).
> - **Link-item stored XSS:** item `url` was stored unvalidated and rendered as an `<a href>` / opened in the website viewer, so a public `javascript:` link item was stored XSS against any visitor who clicked it. Now restricted to http(s) on write (matching profileLinks), with an inert-text render guard in GetInfo as defense in depth.
> - **Secret in GDPR export:** the data export stripped `passwordHash` but left `recoveryCodesHashed` (password-equivalent). Now stripped too.
> - **Agent thread titles:** user-supplied create/rename titles were uncapped (auto titles cap at 60); bounded to 100 to keep the per-user thread-list KV value under its size limit.
> - **Defense in depth:** `nosniff` on all upload serve paths; DOM-apply guards so the appearance store is testable; de-flaked the worker suite against transient non-JSON runtime errors.
>
> New integration coverage: the full auth lifecycle (recovery-code login + regeneration, change-password session invalidation, change-username normalization/uniqueness, cancel-deletion, GDPR export secret-stripping), agent thread CRUD + per-user isolation, fs-scope + patch-field + SSRF boundaries, profile variants round-trip, and the link-URL XSS guard. Frontend: appearance store actions, the visitor transform, and the OAuth state check. Worker suite 20 → 34, frontend 44 → ~310.
>
> Audited and found clean (no bug): bazaar publish/install + estheme, the designTokens/customCSS validators, app storage (KV) sandboxing, profile field filtering, game cross-isolation + sandbox grant, `fsPolicy` glob matching, `getPublicItemsFiltered` (fails closed), the cartridge validator, og:image escaping, the refresh-token rotation + reuse detection, recovery-code entropy, agent chat capability tokens (purpose-bound), analytics dedup, and the sound/cursor serve routes.
>
> **Test harness:** the worker integration suite now runs against a fresh ephemeral `persistTo` temp dir per run (not the shared `.wrangler/state`), so it is hermetic — no state leaks between runs, no dev-account pollution, and the previously flaky/slow `hard-deletes an account…` test (which scanned a KV bloated by accumulated test signups) now runs in ~0.25s and is stable. Note: a large `.wrangler/state` from earlier runs can be cleared; it is no longer written to by tests.
>
> **App-listing exposure fix (2026-11-19, sandbox-review follow-up).** The app bridge's `fs.list` has always skipped `type: 'app'` items (EternalService — "apps don't list themselves to apps"), but the capability-token REST list (`GET /api/apps/:appId/fs/list`) still included them, so an installed app holding a `/**` read grant could enumerate installed app names and ids (reading them already 404s; no manifest/grant data leaked — information exposure only). The REST list now applies the same skip; the owner's own desktop list is unchanged. Audited every app-scoped list surface: the bridge `fs.list` (already skipped), the REST `fs/list` (fixed), REST `fs/read` (item-level, app items 404), `?ft=` file tokens (single-file serving only), and game capability tokens (game saves only). Regression test drives both list paths plus the owner view. While writing it, two harness facts got corrected: the bridge under `unstable_dev` DOES read the same DO state (the earlier "separate DO namespace" note was masking this), and the compiled worker's `clampInt` maps a missing `limit` to 1 (Number(null) is 0, not NaN), so a bare bridge `fs.list` only ever returns the first item — bridge assertions must pass `?limit=500`; that quirk itself is a follow-up, not fixed here.
>
> **Public desktop-items write lockdown (2026-11-19, Workstream 3 Phase B follow-up).** `PATCH/POST /api/desktop/items` forwarded bodies verbatim to the UserDesktop DO's internal `/items` endpoints, whose update allowlist — kept intact for the server-side app flows — accepts `appManifest`, `grantedPermissions`, `permissionGrantedAt`, and `grantedPermissionApprovals`. Any owner session could therefore rewrite an installed app's manifest (declaring scopes the app never shipped, then granting them through the otherwise-honest permissions route), forge grants, or fabricate approval dates: the never-grant-more-than-declared rule, the broad-scope tick, and the approval audit trail were all bypassable. The public routes now reject those fields with a 400 naming them, on create and patch alike; the DO's internal allowlist is unchanged, so dev-deploy, agent installs, release rollback, and the permissions route keep working. Verified the frontend never wrote these fields through this route (app writes go through `/api/apps/*`); the one collateral flow was duplicating an app item, which fabricated a second manifest-carrying item through the public create. **That follow-up landed (2026-11-19):** `duplicateItems` now skips `type: 'app'` items entirely — an app-only selection shows an "Apps can't be duplicated" info alert, a mixed selection duplicates the non-app items and names the skipped apps — and every duplicate is stripped of the four server-managed fields before the create, so no stale local item can trip the gate; the Duplicate affordance (menu bar Edit menu, desktop and folder context menus) is disabled whenever the effective duplicate set is apps only, and the ⌘D shortcut lands on the same skip. The same routes were hardened to 4xx for malformed bodies: a non-JSON create/patch body (previously a 500 from the DO's verbatim `request.json()`) and a patch body that isn't a JSON array (previously a 500 from the DO's iteration) are both answered with a 400 at the route, before any DO forwarding; valid requests forward unchanged. Store regression tests pin app-only, mixed, and normal duplicates plus the field strip; integration tests pin the new 400s and the unchanged valid paths. The Phase B lazy-migration integration test used this very route to craft its pre-Phase-B item (grants with no approval metadata); since no legitimate writer produces that mismatch anymore, the crafting step is gone — the legacy read shape stays pinned by the `resolveGrantApprovals` unit tests (`appScopes.test.mjs`), and the route-level test now pins the still-reachable rules: an already-granted broad scope still needs its tick, and re-approval refreshes the record. **All-or-nothing item batches (2026-11-19, stickertype/dupapp follow-up):** the same writes are now transactional per request. The DO validates the whole PATCH batch up front — entry shape, string `id`, object `updates`, the type-transition, stickerConfig, and URL-safety checks — then applies and persists all surviving entries together; a bad entry answers a 400 naming the entry index and reason and applies nothing. (Previously the URL check ran mid-apply-loop as a plain `Error` — a 500 — after earlier entries were already written to the in-memory map but never persisted, so memory disagreed with storage until the DO restarted; null/shapeless entries 500ed the same way.) Create bodies that are valid JSON but not an object (`42`, `[]`, `"x"`) used to spread into the item defaults and silently create an "Untitled" folder — the route and the DO's client-facing create now answer 400. Unknown item ids and cycle-skipped folder moves keep their silent-skip semantics, unsafe-URL creates/patches are a 400 instead of the old 500, and valid batches are byte-for-byte unchanged.

## How to read this

Four core workstreams, each with: where it stands, what to do (ordered), and what "good" looks like. Underneath them sits **Foundations** — cross-cutting reliability that every workstream depends on. A surface is not "done" until its acceptance bullets have recorded evidence (a test or a logged manual run), not just a passing build.

Verification baseline that already holds (re-run 2026-11-11): both typechecks, frontend build, lint, and all tests pass (21 frontend + 19 worker). The solid substrate — JWT + refresh rotation, bcrypt, per-user `UserDesktop` Durable Object on SQLite, magic-byte upload validation, strict CSP/HSTS/env-aware CORS, public-asset + visitor-WS rate limiting, and Dynamic Workers as the sandboxed app runtime — is real and should not be rewritten.

## Workstream 1 — Core functionality (desktop, windows, files)

The thing EternalOS *is*: a draggable desktop of windows, icons, folders, files, and widgets that survives reload and connection loss.

**Where it stands** (audited 2026-11-19) — ✅ the reliability core is done and test-pinned. The failure matrix (forced offline / 401 / 429 / 500 → rollback to the last server-acknowledged state + a surfaced error, per action) and reconnect convergence without duplicates are pinned by `desktopStore.test.ts` (74 tests as of this audit; the four canonical failures are `test.each`-driven for create/update/move/trash, with restore/empty-trash/cut-paste/upload/sort/privacy covered individually); the settings half lives in `authStore`/`appearanceStore`/`soundStore`/`ProfileWindow`/`QuickStartWizard` tests. Window restoration + resize persistence (`windowStore.test.ts`), deterministic search (`utils/search.ts`), and the body-drag/click contract (`Window.test.ts`) are covered; the store's state model is split (`desktopItemSync.ts`, `desktopSelectionSlice.ts`), and the ContextMenu/AlertDialog keyboard contracts are test-pinned. Remaining (see Open gaps): `Desktop.tsx` (~2,000 lines) still carries interaction, rendering, and commands together; window move/resize has no keyboard path; the desktop icon-navigation shortcuts still fire while a modal is open. Viewers exist for text, code, markdown, PDF, image, audio, video, and websites; widgets for sticky notes, link boards, music, pixel canvas, and a guestbook.

**Do (ordered):**
1. ✅ **Done — R3 closed:** the position-save path now queues through `persistItemMutation`, rolls back to the last server-known position on failure (even across a rapid drag), and surfaces a "Sync Failed" error. A broader saved/saving/failed *status indicator* for editors/settings is still a nice-to-have (deliberately untracked — it is not a "Good when" clause).
2. ✅ **Done — accessibility bugs fixed (both halves test-covered, 2026-11-19):** ContextMenu keyboard nav + menu roles and the AlertDialog focus trap / title linkage / scoped Enter were implemented 2026-11-11 (see the Foundations note). **ContextMenu half:** roles + roving keyboard nav landed with the 2026-11-11 pass; the remaining gaps are now closed — Escape restores focus to the element that had focus before the menu opened, and Tab closes the menu — and the full contract is pinned by `ContextMenu.test.ts` (real component render under the repo's node-env test DOM): `menu`/`menuitem`/`menuitemcheckbox`/`separator` roles with `aria-disabled`/`aria-checked`, initial focus on the first enabled item, ArrowUp/ArrowDown wrap skipping disabled items, Home/End, Enter/Space activation, Escape close + focus restore, Tab close, plus mouse-click activation guards. The menu API has no submenus, so `aria-haspopup`/`aria-expanded` has nothing to apply to. **AlertDialog half:** the same node-env test DOM pins it too (`AlertDialog.test.ts`): `role="alertdialog"` + `aria-modal` + `aria-labelledby`/`aria-describedby` linked to title and message via `useId` (message doubles as the name when there is no title), initial focus on the primary action — the established pattern here, every call site marks its default action primary, à la classic Mac alerts — with a first-action fallback for button sets without a primary, Tab/Shift+Tab wrapping that also pulls escaped focus back inside, Enter activating only the focused button (Enter on Cancel cancels; Enter outside the dialog does nothing — no global Enter listener), Escape cancelling, and focus restored to the opener on close. Remaining follow-up (separate task): Desktop.tsx's document-level icon-navigation shortcuts (Tab/Enter/Escape on selected icons) still fire while any modal is open and need their own gating.
3. ✅ **Harden the reliability matrix with tests** (substantially done): create/delete/update/position, **trash/restore/empty-trash**, and **cut/paste** (`pasteItems`) have optimistic-write rollback + failure surfacing with tests (`desktopStore.test.ts`) — a failed move/trash/restore no longer leaves an item looking moved/(un)trashed when the server never recorded it, and a refused empty-trash restores the trashed items from the acknowledged snapshot (2026-11-19) instead of leaving them gone locally. **Window restoration** across reload / connection-loss is now covered (`windowStore.test.ts`): restores from localStorage, falls back to server windows on a new device / cleared cache, drops windows whose item was deleted, discards corrupt state, and clamps off-screen windows into the viewport. **Deterministic search** is now done: the ranking was extracted from `SearchWindow` into a pure `utils/search.ts` (`searchItems`) and given a total-order tiebreak (score → recency → **id**), so equal scores/timestamps no longer produce non-deterministic ordering; covered by `search.test.ts` (determinism, AND semantics, synonym vs exact ranking, trashed exclusion, limit). **Upload reliability** is covered (`desktopStore.test.ts`): a successful upload adds the item and completes its progress entry; a failed upload leaves no phantom item and marks the entry errored; a late upload after an account switch can't populate the next account. (Worker-side upload validation + quota accounting already have integration coverage.) **Folder creation** goes through `addItem` (a folder is just `type: 'folder'`), so it's covered by the failed-create rollback test. **Resize persistence** is covered (`windowStore.test.ts`): a resize enforces the 200×150 minimum and round-trips through localStorage to survive reload. Rename rides on `updateItem` (partially covered). **Settings half of the "Good when" (2026-11-19):** every user-visible save path outside `desktopStore` was audited against forced offline / 401 / 429 / 500 and the failures fixed, each with a regression test (`authStore.test.ts`, `appearanceStore.test.ts`, `soundStore.test.ts`, `ProfileWindow.test.ts`, `QuickStartWizard.test.ts`): the appearance save no longer mirrors a refused rice into localStorage as if saved (it stays painted-but-unsaved and the caller surfaces the error — the AppearancePanel/CSSEditor pattern); the six optimistic profile setters (wallpaper, wallpaper mode, bio, profile links, share description, analytics — the privacy toggle) now serialize per field, roll back to the last server-acknowledged value on refusal, and report failure so their surfaces can say so (`ProfileWindow` keeps the edits in the editor with an error instead of a false "Saved!", `ShareDialog` shows Saved only on ack, the analytics toggle reverts with a visible error, wallpaper select/upload reports failure); the sound-pack mapping sync moved into the store (`saveCustomSoundPack`) with rollback — this exposed a latent bug where `setCustomSoundUrl` mutated the pack in place, corrupting any previously captured rollback target; the QuickStartWizard no longer commits the preset before the server accepts it (it reverts to the last acknowledged rice on refusal, and its wallpaper is only adopted after the PATCH acks). CSS-history restore was audited clean (applies the reverted profile only on success, shows the error otherwise); the watermark and display-name paths in `PreferencesWindow` were already correct; `themeStore` was vestigial (no consumers, no server sync — theme-selection saves go through the appearance store and the wizard) and has since been deleted outright (2026-11-19). **The W1 reliability matrix is now substantially complete.**
4. ✅ **Separate acknowledged server state from interaction state** in the store (prerequisite for the above being testable); extract desktop commands/persistence from `Desktop.tsx` only as far as the tests need. **State-model split done (2026-11-19):** the store's model is now explicit. The data slice holds the *displayed* (optimistic) items; `desktopItemSync.ts` owns the *server-acknowledged snapshot* (last server-confirmed value per item) plus all pending-mutation bookkeeping — the per-item write queue `persistItemMutation` moved there unchanged in semantics, and rollbacks now target the acknowledged snapshot per attempted field with the existing not-re-touched guards, instead of ad-hoc closure snapshots. The selection moved to `desktopSelectionSlice.ts`, a separate slice sync/reconcile code never writes (`setItems`/`loadDesktop` refresh items + snapshot only; `removeItem`/`moveToTrash` shrink it through `dropFromSelection`; session reset through `deselectAll`) — so interaction state provably survives a server reconcile. Making the rollback target the acknowledged snapshot fixed three real "successful-looking unsaved item" gaps, each pinned by a regression test verified to fail on the old code: two chained renames that both fail used to leave the *intermediate optimistic* name displayed; a rename whose save fails while the user drags the same item used to skip rollback entirely (now the name reverts, the newer move is kept); and a position save failing after an earlier save landed used to leave the newer unsaved position (the old code deleted its rollback target on the first success). Reconcile coverage added (`desktopStore.test.ts`, 44 → 57): server echo after an optimistic create converges to one item (no duplicate), failed writes roll back to the acknowledged snapshot, successful writes/loads refresh it, and interaction state survives both `loadDesktop` and `setItems` reconciles. **The `Desktop.tsx` extraction (deliberately minimal — only as far as the tests need):** its commands/persistence all flow through the store's public actions and the new tests are store-level, so nothing needed lifting except one command (below). **The bypass paths this note left open are closed (2026-11-19, desktopgaps):** the fire-and-forget sort/clean-up saves now persist as ONE batched request registered in every affected item's write queue (`arrangeAndPersist` in `desktopStore.ts`) — the batch fires when the last item's queue turn comes, so it can never overtake an in-flight save for any of its items and later writes land behind it; a refusal is all-or-nothing (the DO's PATCH handler applies the whole batch or, on 401/429/5xx/network, none of it) and reverts every item to the acknowledged snapshot with one shared "Sync Failed"; `emptyTrash` restores the trashed items from the acknowledged snapshot when the server refuses the permanent delete; and the one raw `apiUploadFile` call in `Desktop.tsx` — the "Add Sticker..." flow, mislabeled "wallpaper" above (the actual wallpaper paths go through `setWallpaper`/WallpaperPicker and were already covered) — is extracted to `components/desktop/stickerUpload.ts` and now drives the store's `uploadFile` + `updateItem`, so a refused upload leaves no item ("Upload Failed") and a refused apply rolls the item back to the acknowledged plain image ("Sync Failed"); the old flow's apply silently no-oped because the raw upload never added the item to the store, so stickers never actually appeared. Each fix is pinned by regression tests verified to fail on the old code (`desktopStore.test.ts`, 57 → 69 tests, plus `stickerUpload.test.ts`). Known worker-side follow-up, **now fixed (2026-11-19):** the UserDesktop DO's item PATCH no longer strips `type` silently — an uploaded image may become `type: 'sticker'` with a shape-validated `stickerConfig` (four finite numbers — width/height unbounded above because resizes compound, rotation ±360°, opacity 0–1 — unknown keys rejected, enforced on create as well as PATCH), so an applied sticker persists across reload. Every other type transition — text→sticker, image→app, app→image, folder→sticker, and sticker→image (there is no convert-back action: the frontend's "Remove Sticker" trashes the item) — is rejected with a 400 naming the transition, validated all-or-nothing across the batch; re-asserting an item's current type stays a harmless no-op. Pinned by worker integration tests (`worker.integration.test.mjs`): image→sticker persists through a fresh GET, the forbidden matrix 400s with nothing changed (including a benign field in the same refused patch), and ordinary patches (rename, rotate/resize stickerConfig) are unchanged.

**Good when:** forced offline, 401, 429, and 500 never leave a successful-looking unsaved item or privacy setting — ✅ both halves covered with tests (items: `desktopStore.test.ts` for desktop items; the 2026-11-19 settings-half note above for every save path outside it); reconnect converges to one consistent result with no duplicates — ✅ (`desktopStore.test.ts`: "reconnecting after failures converges to the server state without duplicates", "a server echo after an optimistic write converges to one item with no duplicate"); core actions are keyboard-reachable — 🟡 partly: icon navigation (Tab/Enter/arrows/⌘⌫, `Desktop.tsx:1379–1477`), context menus, dialogs, and the menu bar are (`ContextMenu.test.ts`, `AlertDialog.test.ts`, `MenuBar.test.ts` — F10 + ARIA menubar, 2026-11-19), but windows can't be moved/resized by keyboard and the icon shortcuts aren't gated while a modal is open; the drag never swallows a click on a list row or tab — ✅ (`Window.test.ts`: body-drag threshold contract, three tests, audited 2026-11-19).

## Workstream 2 — Customization

Half the product's personality. Today it spans custom CSS, color tokens, typography, variants, wallpaper, cursors, sounds, sprites, icons, and CSS assets.

**Where it stands** (audited 2026-11-19) — 🟡 Rich, now test-locked, still fragmented at sharing. The token pipeline (`CustomAppearance` → `resolveTokensFromAppearance` → `compileTokensToCSS` → DOM) works and is directly covered (`tokenCompiler.test.ts`); CSS is sanitized and scoped (`cssSanitizer.test.ts`); the save/reload/reset round-trip, CSS-history restore, and the server null-clear protocol are covered (`appearanceStore.test.ts` + the worker suite). The `.estheme` single-file skin format is finished **and test-covered** on the client path — export/import carry CSS + tokens + variants + typography + cursors + sounds + wallpaper as one unit, with unsaved Keep/Revert preview (drag-and-drop included) and fork lineage (`estheme.test.ts`, `exportTheme.test.ts`, `importEstheme.test.ts`, `themePreview.test.ts`); every editor writes back through the pipeline (item 4). Remaining: bazaar still *publishes* a flat token blob rather than accepting full bundles and its install path skips the asset layers (parked marketplace-v2); the `.estheme` icons layer is declared-but-not-applied (warned at import); built-in wallpaper *patterns* and mobile wallpaper variants don't travel (warned); and the preset contrast floor is automated for hex pairs only — the gradient/glass presets (XP, Frutiger Aero) have no recorded manual pass.

**Do (ordered):**
1. ✅ **Preset readability matrix (automated floor done):** every shipped preset is now guarded by `onboardingPresets.test.ts` — structural shape, valid-hex ink colors, a 3.0:1 contrast floor on the authored text/background pairs (title/button/label), a clean token-pipeline compile, and customCSS that sanitizes scoped + remote-free. This caught + fixed a real one (Y2K: white title text on hot pink, 2.65:1 → dark-magenta `#8B0040`, 3.65:1). **Follow-up (optional):** an in-browser manual pass for the gradient/glass surfaces (XP, Frutiger Aero) whose text contrast can't be computed from hex.
2. **Lock down the customization round-trip:** save/reload, reset, CSS sanitization, CSS history restore, and theme import/export each need a test. Sanitizer regressions are a security surface, not just cosmetics. ✅ **Done:** the CSS sanitizer was extracted from `appearanceStore` into a pure, unit-tested `utils/cssSanitizer.ts` (url() allowlisting, `@font-face` stripping, `.user-desktop` scoping — covered by `cssSanitizer.test.ts`), and the save/reload round-trip (`profileToAppearance` ↔ `appearanceToProfileFields`, `buildTokenUpdate`/`getTokenValue` token routing) is covered by `appearanceStore.test.ts`.
